## 2026-11-11: A Player reports it plays animated and video media (#424)

<!-- prawduct: type=feature | scope=player-media-capability | release=v0.11.0 -->

Heartbeat minor 5 adds `capabilities.media`: the kinds of media a display shows
(`image`, `animated`, `video`) and, optionally, the largest video frame it plays
with no dropped frames. Arrt Player is gaining an mpv renderer that plays moving
media, and it sends the capability once a contract tag carries the field.

- **The schema** (`contract/schemas/heartbeat.v1.schema.json`) requires `kinds`
  and allows `video_max_frame` only beside `video`. Two valid fixtures (a Player
  that plays video up to 720p, and one that shows still images only) and three
  invalid ones (an unknown kind, no kinds, a frame limit without video), each
  invalid fixture failing on its named rule alone.
- **The prose** is `player-contract.md` § The heartbeat, minor 5: capabilities
  without `media` read as `kinds: ["image"]`, and a reader ignores a kind it does
  not know.
- **The server is unchanged.** It keeps the heartbeat as it came, and its suite
  posts every valid heartbeat fixture to the real route, so it accepts minor 5.
- **`arrt-contract` 1.1.0**, a package minor.

**Not in this change:** moving media in a feed. Major 2's `media.content_type`
admits only JPEG and PNG and the Library holds no clips, so a clip's duration and
the owner's dwell rule wait for that change; #424 stays open for it.

**Consumer note:**

Arrt Player: pin `contract-v1.1.0` and send `capabilities.media` with
`schema.minor` 5. A server on 1.0.0 accepts it, because it does not check the
key, so the Player may upgrade first.

## 2026-11-09: What Ask's replies cost is written to the spend ledger

<!-- prawduct: type=fix | scope=ask-spend | closes=brookstalley/arrt#337 | release=v0.10.0 -->

Ask showed each reply's cost but never recorded it, so `spend_in_month` and
`art_discovery(action='spend')` under-reported against the provider's bill by
whatever Ask had spent. The owner ruled on 2026-10-09 that Ask's spend counts.

Each reply billed anything now writes one `SpendRecord` in a new category,
`ask_tokens`, holding the sum of its model calls' costs as Decimal, the model
the provider says answered (none when its calls named more than one), and token
counts where the provider reported them.
It is written however the reply ended: answered, stopped at the step limit,
refused, failed or abandoned by its client. A write that fails, in the
service's words or the database driver's, is logged and the reply still ends. `Ask` takes the writer as a required `record_cost`, so
an application that builds one cannot leave it unwired.

**Consumer note:**

The month's spend that Arrt reports now includes what its assistant, Ask, spent.
Nothing is backfilled: replies before this release are not in the ledger.

**Rolling back past this release needs one statement.** A release from before
it refuses to read a spend row in a category it does not know, so the month's
spend fails once Ask has written one. Before starting the previous image, run
`DELETE FROM spend_records WHERE category = 'ask_tokens';` on the catalogue.
That forgets what Ask spent since the upgrade, which the release being rolled
back to never counted anyway. `deploy/README.md` § Ask's spend in the ledger.

## 2026-11-09: Tests that failed now and then under the parallel suite, and one product race behind two of them

<!-- prawduct: type=fix | scope=flaky-tests | closes=brookstalley/arrt#57,brookstalley/arrt#397,brookstalley/arrt#376,brookstalley/arrt#402,brookstalley/arrt#372 | release=v0.10.0 -->

**A product race, fixed (#57, #397).** `DiscoveryRunner.run_status` read a run
and then asked whether it was still in flight. A worker finishing between the
two left the caller a mid-run reading presented as final: status
`resolving_works` and no phase-2 estimate. It now asks first, then reads.
Measured with injected delays; a unit test forces the finish into the window and
fails against the old order.

**Test defects:**
- **#376:** the shapes-republish test compared the wrong pair of feeds and passed only when three publishes fell in one wall-clock second. It now moves a test clock and compares the right pair.
- **#402:** browser tests that left Ask for Walls waited for any page heading, which Ask's own met. They now wait for Walls' heading. A fourth test with the same wait got the same fix.
- **#372:** the suite's one-shot HTTP requests had httpx's 5 s default, which a loaded run reaches (measured: 4.4 s worst at three suites at once). They now take 30 s, set once in `arrt/tests/serving.py`, with a guard that the bound applies and that product code never calls the test-only default.
- A wall-gone browser test deleted its wall before the page had drawn it. It now waits for the wall's card.
- The back-button test in `test_the_sidebar.py` waited for any heading after opening a work, which Walls' own met, so back could run from Walls and pass. It now waits for the Work page's own `← Walls` link, and for it to go after back.

**#371 stays open.** Its second case is probably #372's timeout, unconfirmed.
Its first did not reproduce in four loaded runs, and its cause is not known.

**Consumer note:**

Nothing changes for a household except one fix: a discovery run's status no
longer reports a run as still working, with no estimate, at the moment it
finished.

## 2026-11-09: Household settings, stored and changed at runtime, from the browser or over MCP

<!-- prawduct: type=feature | scope=unattended-settings | closes=brookstalley/arrt#329 | release=v0.10.0 -->

`agents-and-memory.md` item 4, first half (`build-plan-unattended-settings.md`).

**Chunk 01, the settings store.** Settings are declared once, in `SETTINGS`
(`library/services/settings.py`), and stored in a new `settings` table in the
catalogue file. A setting's value is the environment's if it gives one, which
locks the setting; otherwise the stored value; otherwise the default. Each is
read when used, so a change applies with no restart. `GET /api/settings`,
`POST /api/settings/{key}` and a new MCP tool, `art_settings` (`list`, `set`),
read and change them in the same fields. `LABEL_UNITS` is the first setting:
`LibraryFacade` asks for it at each label build. `.env.example` no longer sets
it.

**Chunk 02, Settings › General.** A new page under Settings, after Sources,
lists every setting the server declares, each its own control applied when
chosen. A setting the environment gives shows its value and the variable that
sets it, with no control. *Label units* is the first, which closes #329.
`arrt/tools/ux_walk.py` reached it by link and found it clean in both schemes at
phone and desktop width.

**Chunk 03, unattended work's settings and its allowance.** Four settings under
their own heading on Settings › General: *Unattended work* (off until chosen),
*Monthly allowance* (dollars, never above `MONTHLY_BUDGET_USD`), *How often* and
*Model* (empty is the discovery model). `UnattendedAllowance` answers whether a
piece of unattended work may start: off, no model key, or the month's allowance
passed, counting only the spend of runs started `unattended` (a new
`initiated_by`). `GET /api/unattended` and `art_settings(action='unattended')`
say where it stands. Nothing starts unattended work yet: Watches, the next plan,
will ask it first. `arrt/tools/ux_walk.py` walked the section: its
accessibility scan was clean at phone and desktop width in both schemes.

**Consumer note:**

Arrt's settings can now be changed while it runs, in Settings › General or by
an agent over MCP. **If your environment sets `LABEL_UNITS`, that setting is now
locked to it**, and Arrt says so where you would change it. Remove it from your
env file to choose the units in Arrt instead. The new table is ignored by an
earlier release, so rolling back starts cleanly; but a household that removed
`LABEL_UNITS` from its env file to choose the units here gets the earlier
release's default (imperial) until it sets `LABEL_UNITS` again. Unattended work is off until
you turn it on and give it an allowance; nothing yet runs unattended either way.

Four new environment variables, `UNATTENDED_WORK`, `UNATTENDED_ALLOWANCE_USD`,
`UNATTENDED_CADENCE` and `UNATTENDED_MODEL`, each lock their setting as
`LABEL_UNITS` does; leave them unset to choose in Settings › General.
`.env.example` documents them, commented out. Arrt now refuses to start, naming
the variable, on a `MONTHLY_BUDGET_USD` that is not a number of dollars (NaN,
Infinity) and on an `UNATTENDED_ALLOWANCE_USD` above the month's budget.

## 2026-11-09: Watches, standing requests Arrt runs on a schedule with nobody watching, and the scheduler that runs them

<!-- prawduct: type=feature | scope=watches | closes=brookstalley/arrt#417 | release=v0.10.0 -->

`agents-and-memory.md` item 4, second half (`build-plan-watches.md`), on the
owner's four answers of 2026-11-09: review only, only verdicts shape taste,
browser-only alerts, a cadence and a cap per Watch.

**Chunk 01, the records Watches owed.** `security-model.md` § Prompt Injection
is re-derived for unattended runs (§ The unattended trigger fired): auto-accept
is not offered, a Watch's run holds no verdict tool, and an agent writing a
Watch over MCP is the new path, bounded by the budget and traced by its surface.
`observability-strategy.md`'s push-alert revisit is answered (browser only).

**Chunk 02, a set-aside setting says so (#417).** A stored setting this release
or deployment no longer allows reads as `source` `set_aside` with a
`set_aside_reason`, on the route, over MCP and on Settings › General, and is
logged once per value.

**Chunk 03, Watches stored.** A `watches` table and `discovery_runs.watch_id`,
`WatchService`, `GET/POST /api/watches`, `GET/POST/DELETE /api/watches/{id}`,
and a new MCP tool, `art_watches`. Each write records its surface.

**Chunk 04, the scheduler.** One Library thread, a pass every five minutes,
logging `scheduler.pass` every time. Each due Watch is weighed against the
unattended allowance and its cap, counting what the pass has already started,
and started as an ordinary discovery run, `initiated_by` `unattended`, on the
unattended model; a refusal is stored with its reason. A Watch's run is in
flight only while the runner holds it, so a deployment with no image search
does not hold its Watch for ever. A Watch whose run failed is tried again
within the hour; a server down for days runs a Watch once, not once per missed
slot.

**Chunk 05, Settings › Watches.** A page under Settings, after Sources: a
Watch's words, how often, its cap, on or off, each applied when changed, with
the server's sentence for where it stands, this month's spend, when it is next
due and its last Get; *Remove…* asks first. A Watch's Get and Review say it was
found by a Watch, and runs list it as *Get from a Watch*. An overdue Watch (an
hour past due with nothing tried) and a spent allowance holding one are named
on the status indicator and on Status. `arrt/tools/ux_walk.py` reached the page
by link from six pages and found it clean at phone and desktop width in both
schemes; it walked the empty page only, and the browser suite covers a Watch's
panel.

**Consumer note:**

Nothing runs until you turn unattended work on and give it an allowance in
Settings › General, then write a Watch in Settings › Watches. A Watch never
accepts anything: what it finds waits in To review. A household's agent over
MCP can write and switch on Watches (`art_watches`), as it can change settings;
each write says which surface made it. The scheduler starts with the server.
An earlier release ignores the new table and column, so rolling back starts
cleanly and runs no Watches. `GET /api/health` gains `watches`; runs gain
`watch_id`; `WatchOut` is new. A setting's `source` on `/api/settings` and in
`art_settings` gains a fourth value, `set_aside` (a stored choice this release
or deployment no longer allows, so the default applies), with a new
`set_aside_reason`; a client reading `source` should expect it.

## 2026-11-08: The taste brief over MCP, and Host and Origin checked on every surface but the Player's

<!-- prawduct: type=feature | scope=mcp-household-agents | closes=brookstalley/arrt#53 | release=v0.10.0 -->

`agents-and-memory.md` item 3, so a household's own agent can work against its Arrt
over MCP from inside the LAN. Open question 5 was answered from the code: taste
writes (`art_taste` `set` and `delete`) and verdicts (`art_review(action='set_verdict')`,
which writes observed taste by the owner's rule) were already on MCP. Two things were
missing:
- **`art_taste(action='brief')`** returns the taste as the text Ask's prompt and
  discovery's phase 1 are told, from `TasteService.brief()`.
- **`arrt.http.hosts.HostGuard`** wraps the whole application. It refuses a request
  whose `Host` is not `localhost`, an IP address, or a name in the new
  `CURATION_ALLOWED_HOSTS` (`421`), and one whose `Origin`, when sent, is neither a
  listed name nor the request's own address (`403`).

  The Player's routes, read from the router that mounts them, are exempt, because
  they take the wall's token. This closes the DNS-rebinding vector #53 recorded
  against `/mcp` and `/api`. Binding policy could not close it, because the
  reference deployment publishes the server's port directly for its Player.
  The owner ruled for this fork on 2026-11-08.

**Consumer note:**

Arrt now refuses requests for a name it was not told about, so a web page cannot
take it over through your browser. **If you reach Arrt by a name** (for example
through a reverse proxy), list that name in `CURATION_ALLOWED_HOSTS` before
upgrading, or the browser interface and MCP will refuse you, saying which setting
to change. Reaching it by IP address needs nothing. The walls are not affected.
Agents connected over MCP can now ask for the curator's taste in the same words
Arrt's own assistant is given.

## 2026-11-08: Review's verdicts become taste

<!-- prawduct: type=feature | scope=observed-taste | release=v0.9.0 -->

Item 2 of `agents-and-memory.md`'s order of work, by the owner's rule of
2026-11-08. Every accept and reject re-derives the artist's observed judgment
(`taste.observe_artist`, by `artist_key`): at least 5 rejected and at least 90% of
the artist's verdicts is an observed `declines`, not open to more; the mirror is an
observed `likes`, open to more; anything else withdraws it. A `stated` judgment is
never overwritten (an observed row beside one is withdrawn), and an `inferred` one
is left alone, since nothing can write one again. Startup re-derives every
artist, so existing verdicts become taste on the first start. The Taste screen's
help names review.

**Consumer note:**

After the first start on this version, Taste may show judgments marked "Read from
what you accepted and rejected", with the counts behind each. They reach Ask and
Gets like any other taste. To overrule one, correct it on Taste: your correction
is a stated judgment, which review never overwrites. Forgetting one lasts only
until your next decision on that artist's works, or Arrt's next start, and the
Forget dialog says so.
